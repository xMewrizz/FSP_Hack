# ФСП.Карьера

Прототип платформы для подбора ИТ-специалистов по подтверждённым навыкам. Работодатель описывает потребность, получает кандидатов из подходящих категорий и сам отправляет приглашение с условиями и зарплатой. Категорию кандидата определяют опрос и тест; результаты ФСП могут дополнить профиль.

Проект делаем по [ТЗ ФСП](docs/00-tz-keypoints.md). Интерфейс и основные API запускаются вместе через Docker Compose.

## Что есть сейчас

| Компонент | Состояние |
|---|---|
| Backend | API авторизации, профилей кандидата и компании, публикаций и откликов на вакансии, приглашений, подбора, тестирования, менторской сети и HR-команд. Командные статусы/заметки хранятся отдельно от профиля кандидата |
| ML-сервис | Помогает разобрать потребность и оценивает развёрнутые ответы. При недоступности модели проверка обязательного ответа ожидает ручной оценки; это не считается успешной проверкой |
| Frontend | Кабинеты кандидата и работодателя, адаптивный банк и подбор, тесты и история результатов, HR-команда и карточки кандидатов, отклики и диалоги |
| PostgreSQL и Redis | Запускаются через Compose; PostgreSQL проходит проверку готовности |
| Документация | Описаны API, тестирование и подбор, техническая проверка тестов и [сравнение сортировок](docs/09-ranking-review.md); качество ранжирования на реальных людях ещё не подтверждено |

Демо-режим использует связанный локальный набор кандидатов, откликов, приглашений, тестовых результатов, наставников и диалогов; эти данные не являются записями production. На запущенном Compose проверен путь от регистрации до принятия приглашения. Отдельный бенчмарк B-31 не уложился в заданный в нём порог времени ответа. Команды запуска приведены в [инструкции](docs/03-api-and-run.md).

## Реализованные возможности

- Кандидат управляет профилем и видимостью, указывает навыки, опыт, хобби и образование; может пройти тесты, видеть историю и результаты, откликаться на вакансии и принимать предложения.
- До доступа к материалам теста кандидат подтверждает конфиденциальность. Задания, ответы и решения закрыты от показа до согласия; экран явно запрещает распространять тестовые материалы и скриншоты.
- Работодатель публикует и редактирует вакансии, рассматривает отклики, отправляет персональные приглашения и общается с кандидатами. Контактные данные по приглашению открываются после согласия кандидата.
- Банк кандидатов поддерживает поиск по имени, навыкам, специализации, грейду, формату, городу, образованию, курсу и возрастному диапазону. Подбор показывает релевантность и объяснение совпадений; результаты навыков отображаются на подписанных радарах.
- HR-команда объединяет рабочее пространство компании: владелец приглашает тимлидов и HR, тимлид приглашает HR, а тимлид/владелец назначает HR права просмотра и редактирования по отдельным вакансиям.
- Внутренняя карточка кандидата содержит этап подбора, статус поиска контакта, ручной статус проверки СБ, заметки и обсуждение, доступные участникам HR-команды.
- Этапы найма включают оффер, онбординг, работу с ментором и найм. HR может посмотреть кандидатов-наставников, связанных с компанией откликом или принятым приглашением, если кандидат включил доступность наставничества и публичность профиля.
- Кандидат видит число отправленных откликов и запросов наставникам. Менторская сеть поддерживает каталог, запросы, принятие и переписку.
- В офлайн-демо доступны синтетические профили, заявки, примеры истории тестов, наставники и диалоги; демо-режим не заменяет серверную базу и не синхронизируется между устройствами.

## Ограничения и интеграции

- Подтверждение ФСП ID и получение официальных достижений из реестра не подключены: на демо доступны только тестовые записи. Keycloak/OIDC также остаётся будущей интеграцией.
- Заполнение профиля и резюме доступно, однако автоматический разбор резюме зависит от настроенного ML-сервиса и не должен считаться источником подтверждённых сведений.
- Тестовые задания и пороги требуют валидации на реальных участниках; качество ранжирования также не подтверждено реальными метриками.
- Стадия проверки безопасности в HR-карточке — ручной командный статус, а не подключённая проверка или автоматический вердикт.
- Перед развёртыванием на реальных данных нужно настроить секреты, хранилище, резервное копирование и интеграции отдельно от демо. Подробности — в [архитектуре](docs/01-architecture.md), [правилах тестирования и подбора](docs/02-testing-matching.md) и [плане валидации](docs/04-validation-dataset-model.md).

## Принятый технический подход

- Backend: Python 3.12, FastAPI, PostgreSQL 16, Redis.
- Frontend: React, Vite и Tailwind CSS; исходники добавлены.
- ML-сервис: отдельный Python API. В режиме описания задачи он обращается к Ollama и предлагает навыки с важностью 1–5. Явные грейд, зарплата и формат извлекаются отдельно; работодатель проверяет всё перед сохранением. Если Ollama недоступна, остаётся ручное заполнение. Новые Backend-наборы включают два открытых задания с модельной оценкой. При сбое модели грейд ждёт ручной проверки; подбор уже подтверждённых кандидатов работает без неё.
- Интеграция с ФСП: на демо используется локальный набор тестовых достижений. Привязка учётной записи через Keycloak/OIDC и получение достижений из реестра — разные будущие интеграции; API реестра организаторы не предоставили.

Подробности: [архитектура](docs/01-architecture.md), [тестирование и подбор](docs/02-testing-matching.md), [план валидации](docs/04-validation-dataset-model.md). Сравнение формулы с простой сортировкой — в [отчёте B-14](docs/09-ranking-review.md); отдельный учебный эксперимент с моделями — в [отчёте Романа](docs/15-ranking-model-experiment.md).

## Локальная проверка

Для backend используется `uv`:

```powershell
cd backend
uv sync
uv run pytest -q
uv run uvicorn app.main:app --reload --port 8000
```

После запуска проверить `http://localhost:8000/api/v1/health`, `http://localhost:8000/docs` и работу через Compose на чистой машине.
