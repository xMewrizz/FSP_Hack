# План валидации тестирования и подбора

Здесь план проверки теста и подбора. Подготовлен [синтетический набор](08-synthetic-dataset.md): 60 кандидатов, пять запросов работодателя и все 300 сочетаний «запрос — кандидат». По принятому правилу в подбор попадают только кандидаты с подтверждённым грейдом нужной специализации. Таких пар 12: по четыре на каждый из трёх запросов Backend. В старой выборке из 30 пар их всего четыре, поэтому для оценки порядка кандидатов подготовлены две отдельные формы на все 12 допустимых пар. Независимой разметки и рассчитанных метрик пока нет.

## Что проверяем

| Механика | Вопрос | Как измеряем |
|---|---|---|
| Категоризация | Совпадает ли категория с независимой оценкой? | Доля совпадений специализации и грейда, матрица ошибок |
| Тест | Сохраняется ли грейд при другом варианте? | Доля совпавших грейдов при двух попытках, разброс баллов |
| Задания | Разделяют ли задания участников с разным уровнем? | Доля верных ответов по уровням, разница между группами |
| Подбор | Есть ли релевантные кандидаты в начале списка? | Precision@3 и nDCG@5 по каждой потребности |
| Объяснение | Соответствуют ли указанные причины данным профиля? | Ручная проверка карточек по заранее заданному чек-листу |
| Безопасность | Не раскрываются ли чужие записи и контакты? | Проверки API с разными ролями и статусами |
| Самостоятельная проверка | Сможет ли эксперт пройти тест без помощи команды? | Новый аккаунт, прохождение доступного теста без заданного лимита времени, список обнаруженных ошибок |

## Данные для первого прогона

Подготовлены 60 синтетических кандидатов по трём специализациям и трём грейдам. Пять запросов работодателя — Backend Junior, Backend Middle, Backend Senior, Frontend Middle и DevOps Junior — дают 60 × 5 = 300 сочетаний. Это все возможные пары внутри набора, а не 300 вручную оценённых совпадений. Старая выборка из 30 сочетаний помогает проверить ошибки допуска, но для оценки ранжирования она слишком мала. В наборе есть профили без истории ФСП, кандидаты с неполным резюме, разные города и ожидания по зарплате. Если после первого прогона состав придётся изменить, новую версию фиксируем до сравнения алгоритмов.

Профили и потребности создаёт скрипт с фиксированным seed; параметры и контрольные суммы сохранены в наборе. Варианты заданий и пробные ответы готовим отдельно. Синтетика помогает проверить логику и редкие случаи, но не показывает качество на реальных людях. Жюри должно суметь самостоятельно пройти доступный тест; готового демо-профиля недостаточно.

## Разметка без подгонки

1. Два проверяющих независимо заполняют `relevance_reviewer_1.jsonl` и `relevance_reviewer_2.jsonl` в `ml-service/data/synthetic_v1/`. В каждом файле одни и те же 12 допустимых пар, без балла алгоритма. До завершения обеих форм проверяющие не смотрят оценки друг друга. В поле `label` ставят 0 — не подходит по существенным требованиям, 1 — можно рассмотреть с оговорками, 2 — подходит; в `reason` кратко указывают основание по навыкам, формату и зарплате. Спорные пары обсуждают после независимой оценки, исходные файлы не перезаписывают.
2. Разметку нельзя вычислять той же формулой, которую затем оцениваем. Иначе высокая Precision@3 будет проверкой согласия алгоритма с самим собой.
3. Для грейда независимую оценку получают по отдельной рубрике и ответам, не используя балл проверяемого теста.
4. Разделяем обучающую и проверочную части по кандидатам, чтобы один человек не попадал одновременно в обе через разные пары. Пять потребностей дают мало независимых запросов: результат показываем по каждой и не называем статистически устойчивым.
5. После фиксации набора и разметки не меняем их ради улучшения метрики. Изменения алгоритма и порогов записываем отдельными версиями.

Формы созданы скриптом `python ml-service/prepare_independent_review.py`. Он не перезаписывает существующие ответы. Демо-достижения ФСП в форме помечены как тестовые; они не подтверждают грейд и не должны заменять оценку рабочих навыков. На Frontend и DevOps сейчас нет подтверждённых тестом кандидатов, поэтому для этих направлений качество ранжирования пока оценить нельзя. Даже после заполнения форм четыре кандидата на запрос дадут только предварительные показатели; для обучения модели потребуется больше независимо размеченных потребностей и кандидатов.

После заполнения обеих форм проверяющие сохраняют согласованные оценки в третьем JSONL-файле с полями `pair_id`, `label`, `reason`, не изменяя исходные оценки. Команда `python ml-service/evaluate_independent_review.py --final-labels путь/к/согласованным_меткам.jsonl` проверит наличие всех 12 пар и оснований, покажет расхождения проверяющих и рассчитает Precision@3 и nDCG@5 для текущей и простой сортировки. Без согласованных меток скрипт выводит только число заполненных строк. Результаты и конкретные ошибки затем переносим в `docs/validation-results.md`; автоматический расчёт сам по себе не закрывает В-19.

## Базовая версия и возможное обучение

Сначала сравниваем подбор с простым правилом: категория, подтверждённые результаты теста и наличие достижений ФСП. Затем можно добавить признаки профиля и ручные веса. Обучаемый ранжировщик имеет смысл только при достаточной независимой разметке и отдельной проверочной части. Сравниваем его с простой версией на одних и тех же кандидатах и потребностях. Если используем LLM или эмбеддинги для обработки текста, отдельно проверяем, улучшают ли они результат подбора.

Для теста сначала проверяем ключи и формулировки, затем по реальным прохождениям оцениваем различимость заданий и стабильность результата. Проводить пробные прохождения всей командой ради отметки о готовности банка не нужно. IRT или подгонка порогов по ответам возможны после накопления достаточного числа попыток. Не стоит заявлять калибровку IRT только по симуляции, созданной из тех же предположений, что и сам тест.

## Ориентиры приёмки

Предварительные ориентиры команды: Precision@3 не ниже 0,8 на проверочном наборе, совпадение грейда при повторном прохождении не ниже 0,8. Они могут потребовать пересмотра после согласования разметки и состава теста. Итоговый отчёт должен показывать фактические значения, размер выборки, распределение по запросам и ошибки, даже если ориентир не достигнут. Значения вроде «P@3 = 0,83» или «модель улучшила качество на 5–10 пунктов» нельзя публиковать без выполненного расчёта.
