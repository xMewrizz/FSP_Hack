# План валидации тестирования и подбора

Здесь план проверки теста и подбора. Подготовлен [синтетический набор](08-synthetic-dataset.md): 60 кандидатов, пять запросов работодателя и все 300 сочетаний «запрос — кандидат». По принятому правилу в подбор попадают только кандидаты с подтверждённым грейдом нужной специализации. Таких пар 12: по четыре на каждый из трёх запросов Backend. В старой выборке из 30 пар их всего четыре, поэтому для оценки порядка кандидатов подготовлена отдельная форма на все 12 допустимых пар. Предварительный расчёт приведён в [результатах проверки](validation-results.md); данных о качестве на реальных кандидатах пока нет.

## Что проверяем

| Механика | Вопрос | Как измеряем |
|---|---|---|
| Категоризация | Совпадает ли категория с независимой оценкой? | Доля совпадений специализации и грейда, матрица ошибок |
| Тест | Сохраняется ли грейд при другом варианте? | Доля совпавших грейдов при двух попытках, разброс баллов |
| Задания | Разделяют ли задания участников с разным уровнем? | Доля верных ответов по уровням, разница между группами |
| Подбор | Есть ли релевантные кандидаты в начале списка? | Позиция первого подходящего кандидата, Precision@3 и nDCG по каждой потребности |
| Объяснение | Соответствуют ли указанные причины данным профиля? | Ручная проверка карточек по заранее заданному чек-листу |
| Безопасность | Не раскрываются ли чужие записи и контакты? | Проверки API с разными ролями и статусами |
| Самостоятельная проверка | Сможет ли эксперт пройти тест без помощи команды? | Новый аккаунт, прохождение доступного теста без заданного лимита времени, список обнаруженных ошибок |

## Данные для первого прогона

Подготовлены 60 синтетических кандидатов по трём специализациям и трём грейдам. Пять запросов работодателя — Backend Junior, Backend Middle, Backend Senior, Frontend Middle и DevOps Junior — дают 60 × 5 = 300 сочетаний. Это все возможные пары внутри набора, а не 300 вручную оценённых совпадений. Старая выборка из 30 сочетаний помогает проверить ошибки допуска, но для оценки ранжирования она слишком мала. В наборе есть профили без истории ФСП, кандидаты с неполным резюме, разные города и ожидания по зарплате. Если после первого прогона состав придётся изменить, новую версию фиксируем до сравнения алгоритмов.

Профили и потребности создаёт скрипт с фиксированным seed; параметры и контрольные суммы сохранены в наборе. Варианты заданий и пробные ответы готовим отдельно. Синтетика помогает проверить логику и редкие случаи, но не показывает качество на реальных людях. Жюри должно суметь самостоятельно пройти доступный тест; готового демо-профиля недостаточно.

## Разметка и расчёт

1. В `relevance_reviewer_1.jsonl` находятся 12 допустимых пар без балла алгоритма. В поле `label` стоит 0 — не подходит по существенным требованиям, 1 — можно рассмотреть с оговорками, 2 — подходит; в `reason` указано основание по навыкам, формату и зарплате. Эти оценки подготовлены Codex и подходят для проверки расчёта, но не подтверждают качество продукта.
2. Разметку нельзя вычислять той же формулой, которую затем оцениваем. Иначе высокая Precision@3 будет проверкой согласия алгоритма с самим собой.
3. Для проверки присвоения грейда нужны реальные ответы людей разного уровня и оценка по отдельной рубрике без опоры на балл проверяемого теста. Таких данных сейчас нет.
4. Разделяем обучающую и проверочную части по кандидатам, чтобы один человек не попадал одновременно в обе через разные пары. Пять потребностей дают мало независимых запросов: результат показываем по каждой и не называем статистически устойчивым.
5. После фиксации набора и разметки не меняем их ради улучшения метрики. Изменения алгоритма и порогов записываем отдельными версиями.

Форма создана скриптом `python ml-service/prepare_independent_review.py`. Он не перезаписывает существующие ответы. Пустой `relevance_reviewer_2.jsonl` остался от первоначального плана и в текущем расчёте не используется. Демо-достижения ФСП в форме помечены как тестовые; они не подтверждают грейд и не должны заменять оценку рабочих навыков. На Frontend и DevOps сейчас нет подтверждённых тестом кандидатов, поэтому для этих направлений качество ранжирования пока оценить нельзя. Четыре кандидата на запрос дают только предварительные показатели; для обучения модели потребуется больше размеченных потребностей и кандидатов с независимой оценкой.

Команда `python ml-service/evaluate_independent_review.py --ai-draft` проверяет наличие всех 12 оценок и объяснений, затем считает позицию первого подходящего кандидата, Precision@3 и nDCG для формулы В-14 и простой сортировки. При четырёх кандидатах на запрос позиция первого подходящего человека понятнее, чем один только P@3. API теперь использует ту же формулу; совпадение порядка и баллов проверено отдельным тестом. Эти метрики всё ещё относятся к вымышленным профилям, а не к реальным работодателям. Если кандидатов меньше пяти, указан фактический размер списка и показатель nDCG@min(5,N). Для будущего набора с согласованными оценками предусмотрен параметр `--final-labels`; в текущем расчёте он не используется. Числа и ограничения записаны в `docs/validation-results.md`.

## Базовая версия и возможное обучение

Сначала сравниваем подбор с простым правилом: категория, подтверждённые результаты теста и наличие достижений ФСП. Затем можно добавить признаки профиля и ручные веса. Обучаемый ранжировщик имеет смысл только при достаточной независимой разметке и отдельной проверочной части. Сравниваем его с простой версией на одних и тех же кандидатах и потребностях. Если используем LLM или эмбеддинги для обработки текста, отдельно проверяем, улучшают ли они результат подбора.

Для теста сначала проверяем ключи и формулировки, затем по реальным прохождениям оцениваем различимость заданий и стабильность результата. Проводить пробные прохождения всей командой ради отметки о готовности банка не нужно. IRT или подгонка порогов по ответам возможны после накопления достаточного числа попыток. Не стоит заявлять калибровку IRT только по симуляции, созданной из тех же предположений, что и сам тест.

## Ориентиры приёмки

Предварительные ориентиры команды: Precision@3 не ниже 0,8 на проверочном наборе, совпадение грейда при повторном прохождении не ниже 0,8. Их нужно пересмотреть после независимой оценки и расширения выборки: по предварительной AI-разметке на каждый Backend-запрос приходится только один кандидат с оценкой 2, поэтому Precision@3 не может превысить 1/3, если релевантными считать только оценки 2. Итоговый отчёт должен показывать фактические значения, размер выборки, распределение по запросам и ошибки, даже если ориентир не достигнут. Значения вроде «P@3 = 0,83» или «модель улучшила качество на 5–10 пунктов» нельзя публиковать без выполненного расчёта.
