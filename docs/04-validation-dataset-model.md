# План валидации тестирования и подбора

ТЗ требует собственную процедуру проверки **и её результаты**. Этот файл пока описывает план; датасета, обученной модели и измеренных метрик в репозитории нет. Числа ниже — цели для внутренней проверки, не результаты исследования.

## Что проверяем

| Механика | Вопрос | Как измеряем |
|---|---|---|
| Категоризация | Совпадает ли категория с независимой оценкой? | Доля совпадений специализации и грейда, матрица ошибок |
| Тест | Сохраняется ли грейд при другом варианте? | Доля совпавших грейдов при двух попытках, разброс баллов |
| Задания | Разделяют ли задания участников с разным уровнем? | Доля верных ответов по уровням, разница между группами |
| Подбор | Есть ли релевантные кандидаты в начале списка? | Precision@3 и nDCG@5 по каждой потребности |
| Объяснение | Соответствуют ли указанные причины данным профиля? | Ручная проверка карточек по заранее заданному чек-листу |
| Безопасность | Не раскрываются ли чужие записи и контакты? | Проверки API с разными ролями и статусами |

## Данные для первого прогона

Планируем 60 синтетических кандидатов, распределённых по трём специализациям и трём грейдам, и пять разных потребностей работодателей. Так получится 300 пар для оценки подбора. Данные должны включать профили без истории ФСП, кандидатов с неполным резюме, разные города и ожидания по зарплате. Числа и состав можно изменить, если после первого прогона окажется, что для некоторых потребностей нет релевантных кандидатов. Изменения фиксируются до сравнения алгоритмов.

Профили и потребности создаются отдельным скриптом с сохранённым генератором случайных чисел, его версией и параметрами. Для теста готовятся эталонные задания и варианты; прохождения моделируются отдельно. Синтетика удобна для проверки кода и граничных случаев, но она не доказывает качество на реальных кандидатах.

## Разметка без подгонки

1. До оценки подбора фиксируем критерии релевантности: специализация и грейд, важные навыки, ограничения формата работы и зарплаты. Минимум два участника команды независимо размечают спорные пары, затем разбирают расхождения и сохраняют исходные оценки.
2. Разметку нельзя вычислять той же формулой, которую затем оцениваем. Иначе высокая Precision@3 будет проверкой согласия алгоритма с самим собой.
3. Для грейда независимую оценку получают по отдельной рубрике и ответам, не используя балл проверяемого теста.
4. Разделяем обучающую и проверочную части по кандидатам, чтобы один человек не попадал одновременно в обе через разные пары. Пять потребностей дают мало независимых запросов: результат показываем по каждой и не называем статистически устойчивым.
5. После фиксации набора и разметки не меняем их ради улучшения метрики. Изменения алгоритма и порогов записываем отдельными версиями.

## Базовая версия и возможное обучение

Сначала сравниваем подбор с простым правилом: категория, подтверждённые результаты теста и наличие достижений ФСП. Затем можно добавить признаки профиля и ручные веса. Обучаемый ранжировщик имеет смысл только при достаточной независимой разметке и отдельной проверочной части. Сравниваем его с простой версией на одних и тех же кандидатах и потребностях. Qwen и модель эмбеддингов не обучаются в этом плане; их использование нужно описывать как обработку текста, а не как доказательство качества подбора.

Для теста сначала проверяем рубрики и различимость вариантов экспертно, затем на пробных прохождениях оцениваем стабильность. IRT или подгонка порогов по ответам возможны после накопления достаточного числа попыток. Не стоит заявлять калибровку IRT только по симуляции, созданной из тех же предположений, что и сам тест.

## Ориентиры приёмки

Предварительные ориентиры команды: Precision@3 не ниже 0,8 на проверочном наборе, совпадение грейда при повторном прохождении не ниже 0,8. Они могут потребовать пересмотра после согласования разметки и состава теста. Итоговый отчёт должен показывать фактические значения, размер выборки, распределение по запросам и ошибки, даже если ориентир не достигнут. Значения вроде «P@3 = 0,83» или «модель улучшила качество на 5–10 пунктов» нельзя публиковать без выполненного расчёта.

## Что сохранить для сдачи

Версионированный генератор данных, задания и рубрики, исходную разметку, скрипт расчёта метрик и отчёт `docs/validation-results.md`. В отчёте отдельно указать синтетическое происхождение данных, метод разбиения, базовую версию, результаты и ограничения. Пока этих файлов нет; их создание запланировано в [бэклоге](05-backlog.md).
