# 04 — Валидация: датасет и модели (детально)

## 1. Что доказываем (привязка к оценке)
- Критерий №2 (25%): тест стабилен, разделяет слабых/сильных, грейд сходится с экспертом, варианты одной сложности равны.
- Критерий №1 (35%): в топ-3 подборки попадают релевантные, выдача объяснима.
- Без цифр эти два пункта — «придумали». С цифрами — закрыты.

## 2. Датасет: состав и схема

Генерим скриптом `ml-service/scripts/make_synthetic.py --seed 42 --n 60`, потом 10% руками правим. Веса Qwen и сиды банка отдельно — лика нет.

### 2.1 `candidates.jsonl` — 60 шт (20 Junior / 20 Middle / 20 Senior по TRUE-грейду)
```json
{
  "id": "cand_001",
  "spec": "backend",
  "true_grade": "middle",
  "declared_grade": "middle",
  "true_skills": {"lang": 6, "api": 6, "db": 5, "algo": 4, "tests": 5, "cicd": 3},
  "resume_text": "Backend 4 года, Python/FastAPI, PostgreSQL...",
  "resume_noise": "добавлен лишний Kafka (не знает, для проверки adjacent)",
  "fsp": {"has": true, "events": [{"name": "ИТМО 2024", "place": 3}]},
  "format": "remote", "city": "Москва",
  "salary_expect": [220000, 280000],
  "trust_mock": 0.92, "inconsistency": false,
  "activity_days_ago": 2
}
```
Обязательно добавить: 15 шт без ФСП (проверка кейса «нет истории»), 8 шт с `inconsistency=true` (Senior в резюме, тест 3/10 — для B-19Mock), 10 шт с adjacent-навыком (знает RabbitMQ, не знает Kafka).

### 2.2 `needs.json` — 5 шт (потребности работодателя)
```json
{
  "id": "need_01",
  "spec": "backend", "grade": "middle",
  "text": "Ищем Middle Backend в платформу. Важны Python или Go, PostgreSQL, REST, Docker.",
  "weights": {"api": 5, "db": 5, "lang": 4, "cicd": 3, "tests": 3, "algo": 2},
  "salary": [220000, 280000]
}
```
5 шт: 2 backend (middle/senior), 1 frontend, 1 devops, 1 DS — чтобы показать, что матчинг не только под одну вакансию.

### 2.3 `pairs.csv` — 300 пар (60×5) с разметкой relevance
Разметка двумя шагами:
1. Авто-правило: `relevant=1` если spec совпал И |true_grade - need_grade| ≤ 1 ступень И взвешенный скор по true_skills ≥ порога. Иначе 0. Шкала 0/1/2 (2 = идеал).
2. Вручную проверить 30 спорных пар командой (аналитик + МЛ-1), зафиксировать в `labels_manual.csv`. Это и есть «эталонная разметка команды» из ТЗ + материал для kappa.

### 2.4 `test_bank/` + `attempts.jsonl`
Банк: эталоны с полями `axis, grade_band, difficulty 1-10, variants[4-8], hidden_cases`. Аттемпты: симуляция прохождений — семплируем ответы по true_skills + шум (вероятность правильного = sigmoid(true_skill - difficulty)). Сиды вариантов `hash(user+attempt)` — разные от сида генерации кандидатов, иначе подгон.

## 3. Какую модель обучаем и зачем (Qwen НЕ трогаем)

Qwen2.5:14B и BGE-M3 — заморожены (inference only): перефразировка, извлечение навыков, эмбеддинги. Обучаем только 2 лёгкие модели на CPU за минуты — этого достаточно и честно для хакатона.

### Модель A — Ranker подбора (главная, под 35%)
**Зачем:** обосновать веса скоринга вместо «взяли с потолка 0.5/0.3».
**Фичи на пару (need, cand):** `cosine(emb_need, emb_profile)`, `weighted_test_gap` (по 6 осям с весами 1–5), `fsp_вес`, `trust`, `актуальность`, `salary_overlap`, `adjacent_bonus`.
**Модель:** `LogisticRegression` (baseline) vs `CatBoost/LogReg` с весами — 5-fold CV по кандидатам (не по парам, чтобы не было лика одного человека в train и test).
**Выход:** выученные веса + `P@3` (доля релевантных в топ-3). В презу: baseline ручные веса vs выученные — вторые выше на 5–10 п.п., значит ML не для галочки.
**Фолбэк:** если CatBoost не встанет — оставить ручные веса, в доку честно «baseline», баллы не режут.

### Модель B — Калибровка теста / пороги грейда (под 25%)
**Зачем:** доказать, что варианты равны по сложности и грейд стабилен.
**Модель:** 1PL IRT (Rasch) на `attempts.jsonl` — оцениваем сложность каждого варианта; либо проще — подбор порогов `junior/middle/senior` по ROC на true_grade.
**Проверки:** (a) дисперсия скора внутри вариантов одного эталона мала, (b) retest тем же сидом ≥80% тот же грейд, другим сидом ≥75%, (c) AUC junior vs senior ≥0.8.

## 4. Процедура (скрипты, 1–1.5 дня на МЛ-3 + полдня МЛ-1)
```
make_synthetic.py → candidates/needs/pairs (seed 42, freeze)
  → run_matching.py (baseline vs learned, 5-fold) → metrics.json (P@3, R@5, NDCG@5)
  → run_testsim.py (симуляция CAT-lite, 2 сида) → stability.json (agreement, AUC, kappa)
  → plots.py → docs/validation-results.md + 3 графика в презу
```
Пороги приёмки: P@3 ≥ 0.8, retest ≥ 0.8/0.75, AUC ≥ 0.8, kappa с ручной разметкой ≥ 0.6. Не сошлось — правим веса/пороги, а не подгоняем датасет (сид заморожен, это отдельно проговариваем жюри).

## 6. Простыми словами: что предсказываем, зачем, какие признаки

Qwen2.5:14B и эмбеддинги BGE-M3 — заморожены (только inference: перефразировка заданий, извлечение навыков). Учатся только 2 маленькие формулы на CPU за минуты.

### Модель №1 (главная) — «подойдет ли кандидат под потребность»
**Выход:** одно число 0–1 (те самые 94% у Морозова на скрине). **Вход:** пара (потребность + кандидат).
**Зачем:** отсортировать список. Без модели веса 0.5/0.3 — «с потолка», жюри режет. С моделью: «веса выучили на 300 парах, P@3=0.83».
**7 признаков (всё уже считается):** `cosine` эмбеддингов (0.81), `test_gap` взвешенный по весам 1–5 (-0.4), `fsp` 0/1, `trust` 0.92, `fresh` 0.9 (2 дня назад), `salary_ok` 0/1, `adjacent_bonus` 0.3 (просят Kafka, знает RabbitMQ). Формула `score = w1*cos + ... + w7*adj`, обучение = подобрать `w1..w7` логистической регрессией на 300 парах с известным ответом. В проде: новый кандидат → те же 7 чисел → подставили → отсортировали + «почему» из топ-3 вкладов.

### Модель №2 — «какой грейд по ответам»
**Выход:** 6 баллов 1–10 + грейд. **Вход:** 12–15 ответов (правильно/нет + сложность 1–10). Правильный ответ на сложное весит больше, чем на лёгкое (IRT-лайт). **Зачем:** пороги Junior/Middle/Senior не от балды, а по ROC на 60 синтетах + доказательство, что другой вариант даёт тот же балл (устойчивость к сливу).
