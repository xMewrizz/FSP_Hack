# Тестирование, категория и подбор

Это проект механики для MVP. Первый банк Backend-вопросов и проверки его структуры уже есть, backend запускается через Compose. Результатов проверки точности определения грейда на людях пока нет. Пороги ниже предварительные, их нужно проверить на данных и при необходимости изменить.

## Как проходит тест

1. Кандидат указывает отрасль, специализацию и предполагаемый грейд.
2. Тест зависит от специализации и заявленного грейда, а не от вакансии. Для каждого задания заранее готовим правильный ответ, правила оценки и несколько вариантов с сопоставимой задумкой; равную сложность ещё предстоит проверить.
3. При новой попытке выбираются другие варианты. Ключ выбора стабилен внутри одной попытки и не использует встроенный `hash()` Python: тот может менять значение между процессами. Идентификаторы варианта и версии задания сохраняются вместе с ответом.
4. Кандидат получает баллы по навыкам и объяснение результата. Сейчас подготовлены только задания с выбором ответа, которые проверяются по ключу. Задания с развёрнутым ответом и проверка ответа LLM запланированы отдельно как P1; до внедрения нельзя описывать их как работающую часть теста. Во время теста новые задания не генерируем.
5. Система сравнивает результат с порогами грейда. Пороги и сложность вариантов уточняются после валидации, а не подбираются под демонстрационные ответы.

Для первого сквозного сценария достаточно покрыть выбранные направления и несколько описаний потребностей работодателя. Сейчас подготовлены четыре исходных Backend-вопроса на каждый из трёх грейдов и по два дополнительных варианта каждого. API меняет вариант при следующей попытке и сохраняет его в записи попытки. После третьей попытки цикл повторяется, поэтому смена вариантов не гарантирует защиту от утечки ответов. Разбор и ограничения — в [банке заданий](07-question-bank.md). Требование «500–1000 заданий» в ТЗ отсутствует.

ТЗ не устанавливает длительность теста и позволяет команде выбрать формат заданий. Первый банк проверяет только ограниченный набор тем; результат такого теста сам по себе не доказывает, что человек владеет всеми навыками уровня Senior. В P1 добавляем задания, где кандидат пишет ход решения или код текстом. Модель сверяет ответ с критериями и даёт объяснение, а спорные ответы рассматриваются вручную. Оценку модели нужно сравнить с заранее проверенными примерами, прежде чем она повлияет на грейд. Если модель недоступна, открытый ответ ждёт ручной проверки.

## Грейд и повторные попытки

Категория — это специализация и подтверждённый грейд. Заявленный грейд храним отдельно. Если кандидат не сдал тест, грейд ниже не присваиваем: предлагаем пройти тест на него. До этого кандидат остаётся в поиске с пометкой «грейд не подтверждён» и идёт после тех, кто прошёл тест.

Для повышения предлагаем отдельный тест. Подтверждённый грейд можно менять не чаще раза в 90 дней. Неудачная попытка и тест на уровень ниже не запускают отсчёт. Правила повторной попытки на тот же уровень ещё нужно описать.

## Почему варианты можно сравнивать

Параметры меняют исходные данные задачи, но сохраняют проверяемое умение и рубрику. Для каждого варианта команда проверяет, что он решаем, ответ однозначен, а сложность близка к эталону. На пробных прохождениях сравниваются доли успешных ответов и результаты повторного теста. Если данных для статистической калибровки мало, используем экспертную проверку и так и называем её; IRT не заявляем до появления достаточного числа попыток. Перефразировка нейросетью сама по себе не защищает от распространения ответов.

## Подбор

1. Работодатель задаёт специализацию, грейд, стек, важность навыков и диапазон зарплаты для предложения.
2. Сначала показываем кандидатов с подтверждённым грейдом. Остальных можно найти с пометкой «не подтверждён». Резюме дополняет профиль, но категорию определяет тест.
3. Внутри категории рассчитывается соответствие по результатам теста и требованиям работодателя. Подтверждённые достижения ФСП могут дать дополнительный вес; отсутствие истории не снижает базовую оценку. Ожидания по зарплате учитываются, только если кандидат их указал.
4. Карточка объясняет конкретные совпадения и пробелы. Процент соответствия появляется лишь после определения шкалы и проверки калибровки; примерные «94%» и «0,92 доверия» в макетах не являются измеренными результатами.
5. Фильтры уточняют текущую подборку. Параметры потребности и фильтров сохраняются в URL или в сохранённом запросе, чтобы пользователь мог вернуться к результату.

Сначала задаём веса подбора вручную и записываем, почему выбрали именно их. Обучать ранжирование стоит после разметки пар «потребность — кандидат»; тогда сравним его с ручными весами. Как будем проверять качество, описано в [плане валидации](04-validation-dataset-model.md).
