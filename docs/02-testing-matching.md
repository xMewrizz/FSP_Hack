# Тестирование, категория и подбор

Это проект механики для MVP. Алгоритмы и пороги ниже нужно проверить на данных и при необходимости изменить; работающих тестов и результатов в репозитории пока нет.

## Как проходит тест

1. Кандидат указывает отрасль, специализацию и предполагаемый грейд.
2. Система собирает тест на этот грейд из банка заданий. У каждого эталона есть проверенный ответ, рубрика оценки и несколько параметризованных вариантов сопоставимой сложности.
3. При новой попытке выбираются другие варианты. Ключ выбора стабилен внутри одной попытки и не использует встроенный `hash()` Python: тот может менять значение между процессами. Идентификаторы варианта и версии задания сохраняются вместе с ответом.
4. Проверка выдаёт баллы по навыкам и объяснение результата. Для закрытых вопросов и кода применяются заранее заданные ответы и проверки; открытые ответы оцениваются по рубрике с возможностью ручной проверки. Языковая модель может предложить формулировку, но не утверждает задание и не меняет балл без проверяемого правила.
5. Система сравнивает результат с порогами грейда. Пороги и сложность вариантов уточняются после валидации, а не подбираются под демонстрационные ответы.

Для первого сквозного сценария достаточно покрыть выбранные направления и несколько описаний потребностей работодателя. Размер банка фиксируется после проверки покрытия: требование «500–1000 заданий» в ТЗ отсутствует. Если банк мал, это нужно прямо показать как ограничение демонстрации, а не заявлять устойчивость к утечке без проверки.

## Грейд и повторные попытки

Категория — пара «специализация + подтверждённый грейд». Заявленный грейд хранится отдельно. Если кандидат не подтвердил заявленный уровень, система **не присваивает ему автоматически уровень ниже**: она предлагает пройти отдельный тест на него. До подтверждения показывается статус «грейд не подтверждён», а не выдуманная категория. Уверенный результат даёт возможность пройти проверку на уровень выше. Выбранное командой правило — не чаще одного изменения подтверждённого грейда за 90 дней. Порядок обычных повторов теста и технических пересдач описывается отдельно до реализации.

## Почему варианты можно сравнивать

Параметры меняют исходные данные задачи, но сохраняют проверяемое умение и рубрику. Для каждого варианта команда проверяет, что он решаем, ответ однозначен, а сложность близка к эталону. На пробных прохождениях сравниваются доли успешных ответов и результаты повторного теста. Если данных для статистической калибровки мало, используем экспертную проверку и так и называем её; IRT не заявляем до появления достаточного числа попыток. Перефразировка нейросетью сама по себе не защищает от распространения ответов.

## Подбор

1. Работодатель задаёт специализацию, грейд, стек, важность навыков и диапазон зарплаты для предложения.
2. Система рекомендует подходящие категории и показывает кандидатов с подтверждённой категорией. Резюме может добавить сведения о навыках, но не заменяет результат теста при присвоении категории.
3. Внутри категории рассчитывается соответствие по результатам теста и требованиям работодателя. Подтверждённые достижения ФСП могут дать дополнительный вес; отсутствие истории не снижает базовую оценку. Ожидания по зарплате учитываются, только если кандидат их указал.
4. Карточка объясняет конкретные совпадения и пробелы. Процент соответствия появляется лишь после определения шкалы и проверки калибровки; примерные «94%» и «0,92 доверия» в макетах не являются измеренными результатами.
5. Фильтры уточняют текущую подборку. Параметры потребности и фильтров сохраняются в URL или в сохранённом запросе, чтобы пользователь мог вернуться к результату.

На старте можно использовать прозрачную формулу с заранее записанными весами. Обучаемая модель ранжирования — следующий шаг, если появится независимая разметка пар и проверка, что качество лучше простого правила. Результаты экспериментов и их ограничения описываются в [плане валидации](04-validation-dataset-model.md).
