# 00 — Ключевые моменты ТЗ (выжимка для команды)

Дата разбора: 2026-10-05. Полный текст — PDF ТЗ ФСП 2026 (8 стр.).

## 1. Что строим
Самостоятельная платформа (не парсинг чужих вакансий), связывающая напрямую работодателя и соискателя. Два кабинета: Кандидат, Работодатель.

## 2. Что реально оценивается (куда вкладываемся)
| # | Критерий | Вес | Что смотрят |
|---|---|---|---|
| 1 | Новая механика подбора | 35% | Сценарий «работодатель сам приглашает», ранжирование, объяснимость. Проверка: топ выдачи на парах вакансия–кандидат + живой сценарий + юзабилити-тест жюри |
| 2 | Тестирование + валидация + категоризация | 25% | Устойчивость к сливу, стабильность грейда при ретесте, дискриминативность, соответствие экспертной разметке, своя процедура валидации с цифрами |
| 3 | Интерфейс | 10% | Понятный сквозной путь без пояснений |
| 4 | Техпроработка | 7% | Код, скорость, масштабируемость, интеграции |
| 5 | Полнота + доки | 6% | Путь соискателя целиком, обработка «нет ФСП-истории», доки по списку |
| 6 | Допы | 7% | Отклики/вакансии, микро-задачи, антифейк, ATS, адаптив |
| 7 | Питч | 10% | Ясность механик + демо |

Вывод: 60% — это подбор + тестирование. Красивый фронт без этих двух механик не вытащит.

## 3. Механика подбора (ядро)
- Работодатель описывает потребность (стек, специализация, грейд, команда) → система дает категории + конкретных кандидатов + обоснование.
- Кандидат в выдаче потому что: совпал по категории (из теста, не из резюме) + скоринг соответствия + вес ФСП.
- Обязательно: фильтры (специализация/грейд/стек/ФСП/доверие), объяснение («почему в подборке», «зона роста: CI/CD 6 из 7»), сортировка по релевантности, % совпадения, оценка доверия (0.92).
- Контакт: приглашение с зарплатой и описанием, без обязательной вакансии. Контакты — только после принятия.

## 4. Механика тестирования (ядро №2)
- Путь: опрос (отрасль/специализация) → заявляешь грейд → тест на него.
- Запрещены: один набор на всех; голая LLM-генерация без контроля сложности.
- Наш путь (фиксируем): банк заданий по осям (Язык/API/БД/Алгоритмы/Тесты/CI-CD) × уровни × параметризованные варианты + LLM только для перефразировки/вариантов с якорением сложности + IRT-калибровка. Детали в `02-testing-matching.md`.
- Правила: грейд не понижается автоматом; не сдал → downshift-тест; сдал уверенно → upshift; кулдаун 90 дней.
- Микро-задачи от работодателей — поддержка актуальности (в MVP минимум: показать механику).

## 5. Данные и видимость (hard rules, иначе провал ТЗ)
- Зарплата от–до ₽ обязательна везде.
- Статусы: отправлено/просмотрено/принято/отклонено.
- Email-регистрация с подтверждением. Модерация/верификация компаний в MVP — skip.
- Справочники специализаций/грейдов — свои, на MVP только основные (Backend/Frontend/DevOps × Junior/Middle/Senior).
- Датасетов нет — генерим синтетику + своя валидация с метриками.

## 6. Техтребования
- Стек свободный, но ML/NLP — плюс. Наш стек зафиксирован в README.
- Frontend + Backend + Хранение, Docker + docker-compose желательны (делаем).
- OpenAPI/Swagger обязателен. 152-ФЗ: согласие, разделение ролей, хеши паролей.
- Десятки concurrent пользователей, «приемлемое» время подборки/поиска/профиля.
- Keycloak-совместимость приветствуется (закладываем OIDC-абстракцию под ФСП ID, но свой JWT сейчас).

## 7. Сдача
Промежуточная: репо + описание механик + базовый сценарий. Финальная: репо + преза + деплой/видео + доки (7 пунктов из ТЗ 3.4).

## 8. Риски для нас
- Qwen 14B локально у сокомандника — бутылочное горлышко (VRAM, аптайм на демо). Нужен фолбэк: кэш вариантов + rule-based скоринг без LLM.
- Синтетика для валидации должна быть честной (разделить seed для банка и для теста, иначе жюри поймает на подгоне).
- Контакты/зарплаты — легко нарушить в API, нужен тест на видимость.
