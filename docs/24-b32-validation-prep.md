# Подготовка проверки качества (B-32)

## Что уже можно проверить

Код расчёта грейда и подбора, тестовые наборы и сценарии прохождения работают. Сравнение моделей для развёрнутых ответов проведено на подготовленных примерах. Это не показывает, насколько система различает опыт реальных людей и как работодатели оценят подборку.

В репозитории опубликован **демонстрационный банк**. Его задания, ключи и эталоны видны в текущих файлах и истории Git. Удаление их из последнего коммита не сделает их секретными. Результаты прохождения этого банка нельзя использовать как независимое подтверждение грейда для человека, которому доступен код.

## Закрытый банк для реальной проверки

Backend поддерживает второй режим: `ASSESSMENT_BANK_MODE=private`. В нём задания и ответы загружаются из JSON-файла, который не входит в репозиторий. Файл содержит `version: 1`, уникальный `bank_id`, `closed_variants` по кодам семей и `open_questions` по кодам развёрнутых заданий. Условия, варианты ответов, ключи, объяснения, критерии и эталоны находятся в этом файле. Каркас JSON соответствует словарям, возвращаемым `prepared_variants()` и `get_open_question_by_code()`; файл с демонстрационными ответами нельзя считать новым закрытым банком.

Перед запуском сервис проверяет наличие каждого задания выбранных базовых наборов и пересдачи, минимум два разных закрытых варианта на семью, корректность ключей, состав критериев и соответствие специализации и грейду. При неполном файле сервис не запускается. У каждого набора в базе сохраняется `bank_id`; сервис откажется работать с историей другого банка. Для закрытого режима используйте отдельную базу: подтверждённые грейды, полученные на демо-банке, переносить нельзя.

Файл можно хранить, например, в локальном каталоге `private-bank/` — он исключён из Git. Для Compose задайте абсолютный путь `ASSESSMENT_BANK_HOST_FILE` в локальном `.env` и запустите:

```bash
docker compose -p fsp-private -f docker-compose.yml -f docker-compose.private-bank.yml up --build -d
```

На локальной машине собран новый банк: 303 семейства закрытых заданий, по два варианта на каждое, и 32 открытых задания. Закрытые варианты и ключи просмотрены вручную, исправлены найденные ошибки. Для 10 заданий с кодом добавлены отдельные закрытые тестовые случаи; эталонные решения прошли 60 случаев в изолированной среде. Это проверка содержания и работоспособности, а не доказательство того, что тест различает грейды. Для этого всё ещё нужны ответы людей с независимо установленным уровнем.

## Как считать результаты, когда появятся участники

Для каждого прохождения сохраняется обезличенный `attempt_id`, специализация, выбранный грейд, решение системы и независимое решение проверяющего по этому же грейду. Файл JSONL состоит из строк такого вида:

```json
{"attempt_id":"attempt-001","specialization":"Backend","target_grade":"middle","system_passed":true,"independent_passed":false}
```

Команда `python ml-service/evaluate_grade_validation.py --input <путь-к-файлу>` считает отдельно совпадения, случаи подтверждения грейда только системой и случаи подтверждения только независимой оценкой. Отсутствующие оценки и повторяющиеся ID отклоняются; пустой файл не даёт метрик.

Для подбора уже есть формы `ml-service/prepare_independent_review.py` и расчёт `ml-service/evaluate_independent_review.py`. Они теперь принимают `--data-dir`, чтобы использовать отдельный обезличенный набор с файлами `candidates.json`, `needs.json` и `all_pairs.jsonl` той же структуры, что в `ml-service/data/synthetic_v1`. Форма для одного независимого оценивающего создаётся с `--reviewers 1`. Ему показывают потребность и профиль без балла сортировки; он ставит 0, 1 или 2 с короткой причиной. После заполнения `relevance_reviewer_1.jsonl` сравнение запускается с `--final-labels` и этим же файлом. Если есть два оценивающих, их формы сравниваются и разногласия разбираются до расчёта метрик. На подготовленных AI-метках команда `--ai-draft` разрешена только для старого синтетического набора.

Пока таких прохождений и оценок нет, цифр качества B-32 нет. При появлении данных сравниваем B-14 и простую сортировку на одних и тех же допустимых кандидатах, показываем число пар, P@3, nDCG и конкретные ошибки. Пороги 75% и 50% пересматриваем только по этой проверке, а не по синтетике.
