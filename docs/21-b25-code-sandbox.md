# B-25: проверка заданий с кодом

В репозитории есть банк скрытых тестов и прототип проверки кода. Прежний вариант запускал ответ кандидата подпроцессом backend: AST-фильтр и таймаут не ограничивали доступ к файлам, сети и памяти. Запуск этого варианта из пользовательских маршрутов убран.

Подготовлен отдельный Docker-исполнитель. Контроллер принимает все 11 заданий с исполняемым контрактом из текущего банка, включая Backend и Data Science; для каждой проверки создаёт новый контейнер. Одновременно могут выполняться не более двух попыток. Два задания пересдачи Senior про псевдокод и архитектуру переведены в развёрнутый ответ: их условия не задают исполняемой сигнатуры и результата. Проверка кода оценивает поведение на изменяемых входных данных, а модель отдельно оценивает решение по критериям задания.

Внутри контейнера код кандидата работает с правами отдельного пользователя. Ожидаемые ответы вычисляет другой процесс, который выбирает новые входные данные для каждой попытки. Кандидатский код получает входные данные, но не ожидаемые ответы. Старые фиксированные тесты остались в репозитории для локальной проверки прототипа; рабочий исполнитель их не использует. Контейнеру запрещена сеть, файловая система доступна только для чтения, временная директория ограничена по размеру. Ограничены память, CPU и число процессов. Контейнер не получает переменные backend и тома с базой. Для задач Data Science отдельный образ содержит NumPy, Pandas и scikit-learn; число вычислительных потоков ограничено. Кандидат видит число пройденных проверок без названий тестов и вывода процесса. Свои тесты через API отправить нельзя.

Исполнитель включается отдельным профилем Compose: `docker compose --profile sandbox up --build -d`. Backend в Compose обращается к `http://sandbox-controller:8002`; адрес можно переопределить через `SANDBOX_SERVICE_URL`. Если профиль выключен или исполнитель недоступен, пробный запуск отвечает `503`. При отправке обязательного задания через очередь ответ сохраняется, а проверка остаётся незавершённой до восстановления исполнителя и повторного запуска. Код с исполняемым контрактом нельзя засчитать по одному ответу модели. Backend сам этот код не исполняет.

Сквозная проверка на работающем Docker прошла для эталонных решений всех 11 исполняемых задач, неверного ответа, подделки строки результата, бесконечного цикла, попытки выделить слишком много памяти и отказа для задания без исполняемого контракта. Дополнительно проверены отсутствие Docker-сокета, сети, секретов и привилегий у процесса кандидата, сохранение работоспособности исполнителя после ошибки и удаление контейнеров после попыток. Итоговый балл за исполняемое задание равен меньшему из двух результатов: доле пройденных скрытых тестов и оценке модели по критериям. Код с нулём пройденных тестов не может подтвердить грейд даже при высокой оценке модели. Доступные в репозитории алгоритмы генерации проверок не следует считать секретом; повторение и обмен ответами учитываются отдельно при разработке теста на грейд.
