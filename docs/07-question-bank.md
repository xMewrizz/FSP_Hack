# Банк заданий Backend

Для первого теста подготовлены задания по Backend на Junior, Middle и Senior. В `backend/app/core/question_bank.py` лежат 12 исходных вопросов. В `backend/app/core/question_variants.py` для каждого есть ещё два варианта с другими исходными данными. API выбирает очередную версию при новой попытке. Итого: Junior — 4 темы и 12 версий, Middle — 4 темы и 12 версий, Senior — 4 темы и 12 версий.

Каждый вопрос сейчас закрытый, с одним правильным ответом. За точный ответ даётся полный вес вопроса, за другой — ноль. Правило оценки и проверяемый навык записаны рядом с вариантами. Вес Junior — 1, Middle — 1,5, Senior — 2; порог подтверждения грейда и пригодность таких весов нужно отдельно проверить на пробных прохождениях.

## Проверка исходных вопросов

| Код | Навык | Решение | Причина |
|---|---|---|---|
| BE-JR-01 | ACID | Уточнён | Сбой процесса не равен физическому уничтожению хранилища. Убрано обещание сохранности после любого аппаратного сбоя. |
| BE-JR-02 | Коллекции Python | Заменён | Каждая версия проверяет сложность одной операции: `append`, поиск в списке или поиск в `set`. |
| BE-JR-03 | HTTP | Оставлен | Метод PUT и его идемпотентность проверяются по понятному условию. |
| BE-JR-04 | Git | Оставлен | Ответ однозначен; тема полезна для работы разработчика, но сама по себе слабо различает грейды. |
| BE-MID-01 | Асинхронный Python | Уточнён | Блокируется конкретный event loop; другие процессы сервера могут продолжать работу. |
| BE-MID-02 | Индексы PostgreSQL | Заменён | Прежний ответ исключал использование `(city, age)` для поиска по `age`, хотя возможен skip scan. Новый вопрос спрашивает про индекс с нужным ведущим полем. |
| BE-MID-03 | Кэш | Заменён | Вместо узнавания названия cache stampede все версии считают обращения к БД при группировке запросов по ключу. |
| BE-MID-04 | SQLAlchemy | Заменён | Версии сравнивают результат `rollback()`, `flush()` и `commit()`. `commit()` сам вызывает `flush()` при необходимости. |
| BE-SR-01 | Повтор денежной операции | Заменён | Прежний вопрос требовал универсального выбора «CP по CAP». Новые версии разбирают откат, потерянный ответ и изменение параметров при том же ключе. |
| BE-SR-02 | Согласованное хеширование | Заменён | Вместо узнавания названия алгоритма все версии оценивают долю переносимых ключей. Условие оговаривает случайное равномерное распределение. |
| BE-SR-03 | Circuit breaker | Заменён | Вместо узнавания состояния Open все версии требуют проследить переходы по заданному правилу. Сложность для Senior проверить на пилоте. |
| BE-SR-04 | Транзакционный outbox | Добавлен | Три версии проверяют откат общей транзакции, отложенную и повторную доставку. |

Источники для спорных фактов: [индексы PostgreSQL](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html), [asyncio](https://docs.python.org/3/library/asyncio-task.html), [HTTP RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [git reset](https://git-scm.com/docs/git-reset), [защита кэша от одновременного промаха](https://redis.io/docs/latest/develop/use-cases/cache-aside/php/), [Circuit Breaker](https://martinfowler.com/bliki/CircuitBreaker.html), [транзакционный outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html). Это проверка технических фактов, а не доказательство одинаковой сложности вариантов.

## Что проверено и что ещё предстоит

- [Лист с 36 вопросами](09-question-review-sheet.md) сохранён для просмотра и возможной будущей проверки; заполнять его участникам команды не требуется. Лист можно пересобрать командой `python backend/generate_question_review_sheet.py` из корня репозитория.
- [Ключи 36 вариантов сверены с источниками](10-question-verification.md). Это проверка фактов, а не независимая оценка сложности. Участникам без опыта Backend не нужно решать вопросы ради формальной отметки.
- Автоматические проверки требуют уникальных кодов, корректных ключей ответов, трёх версий каждого Backend-вопроса и покрытия всех трёх грейдов. Они работают без БД.
- При новой попытке API выбирает следующую из трёх подготовленных версий каждой темы и сохраняет её код, текст и ключ в сессии. После третьей попытки версии повторяются; это не защита от распространения ответов.
- Чтобы судить о сложности и порогах грейда, нужны реальные ответы людей разных уровней. Это задача валидации B-19, а не условие готовности подготовленного банка. Без таких данных банк нельзя называть статистически откалиброванным.
- Вопросы Frontend и DevOps сохранены, но в каждой паре сейчас только по одному исходному вопросу. Эти направления не открыты для теста в B-01.
- Текущие задания проверяют ограниченный круг тем и не проверяют написание и отладку кода. Их результат не равен полной оценке квалификации Senior. Задания с развёрнутым ответом или фрагментом кода и проверкой по критериям с помощью LLM запланированы в P1 (B-27); спорные оценки должны попадать на ручной разбор.
