# Банк заданий Backend

Для Backend подготовлены 132 семьи вопросов с выбором ответа, по три варианта на семью — всего 396 текстов. В базовом наборе каждого грейда четыре обязательных навыка по десять самостоятельных вопросов. Junior дополнительно решает два открытых задания, Middle и Senior — три, включая рабочую ситуацию. Варианты одного вопроса не увеличивают число самостоятельных заданий. Ещё три вопроса Git доступны как дополнительный навык Junior; остальные вопросы старого общего теста остаются для совместимости. Прежний маршрут выдаёт свои 12 заданий одной сессией, но грейд не присваивает. Открытые задания хранятся в `open_question_bank.py` и `open_question_alternates.py`.

Прежний банк собирался под один общий тест с разными темами на каждом грейде. Для нового набора выбраны четыре постоянных блока: Python для Backend, SQL и работа с данными, HTTP API и интеграция, надёжность сервиса. Недостающие пары Senior/Python, Senior/SQL, Middle/API и Junior/надёжность закрыты новыми заданиями. Имеющиеся задания Git не переименованы в «надёжность»: они доступны как отдельный дополнительный тест Junior после подтверждения грейда. Распределение заданий по блокам и их способность различать грейды нужно ещё проверить с профильными специалистами. Python для Data Science хранится как отдельный навык; его банк вместе с остальными навыками направления описан в [документе Data Science](17-data-science-question-bank.md).

Каждый из 40 вопросов базовых навыков закрытый, с одним правильным ответом. За точный ответ даётся полный вес вопроса, за другой — ноль. Вес Junior — 1, Middle — 1,5, Senior — 2; между грейдами эти исходные баллы напрямую не сравниваются. Результат каждого навыка нормализуется к 10 баллам. Каждое открытое задание также даёт до 10 баллов. Для грейда нужно не менее 75% от максимума набора и не менее 50% на каждом шаге. Порог и пригодность заданий нужно проверить на ответах людей разных уровней.

## Проверка исходных вопросов

| Код | Навык | Решение | Причина |
|---|---|---|---|
| BE-JR-01 | ACID | Уточнён | Сбой процесса не равен физическому уничтожению хранилища. Убрано обещание сохранности после любого аппаратного сбоя. |
| BE-JR-02 | Коллекции Python | Заменён | Каждая версия проверяет сложность одной операции: `append`, поиск в списке или поиск в `set`. |
| BE-JR-03 | HTTP | Оставлен | Метод PUT и его идемпотентность проверяются по понятному условию. |
| BE-JR-04 | Git | Оставлен | Ответ однозначен; тема полезна для работы разработчика, но сама по себе слабо различает грейды. |
| BE-MID-01 | Асинхронный Python | Уточнён | Блокируется конкретный event loop; другие процессы сервера могут продолжать работу. |
| BE-MID-02 | Индексы PostgreSQL | Заменён | Прежний ответ исключал использование `(city, age)` для поиска по `age`, хотя возможен skip scan. Новый вопрос спрашивает про индекс с нужным ведущим полем. |
| BE-MID-03 | Кэш | Заменён | Вместо узнавания названия cache stampede все версии считают обращения к БД при группировке запросов по ключу. |
| BE-MID-04 | SQLAlchemy | Заменён | Версии сравнивают результат `rollback()`, `flush()` и `commit()`. `commit()` сам вызывает `flush()` при необходимости. |
| BE-SR-01 | Повтор денежной операции | Заменён | Прежний вопрос требовал универсального выбора «CP по CAP». Новые версии разбирают откат, потерянный ответ и изменение параметров при том же ключе. |
| BE-SR-02 | Согласованное хеширование | Заменён | Вместо узнавания названия алгоритма все версии оценивают долю переносимых ключей. Условие оговаривает случайное равномерное распределение. |
| BE-SR-03 | Circuit breaker | Заменён | Вместо узнавания состояния Open все версии требуют проследить переходы по заданному правилу. Сложность для Senior проверить на пилоте. |
| BE-SR-04 | Транзакционный outbox | Добавлен | Три версии проверяют откат общей транзакции, отложенную и повторную доставку. |

Источники для спорных фактов: [индексы PostgreSQL](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [SQLAlchemy Session](https://docs.sqlalchemy.org/en/20/orm/session_basics.html), [asyncio](https://docs.python.org/3/library/asyncio-task.html), [HTTP RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [git reset](https://git-scm.com/docs/git-reset), [защита кэша от одновременного промаха](https://redis.io/docs/latest/develop/use-cases/cache-aside/php/), [Circuit Breaker](https://martinfowler.com/bliki/CircuitBreaker.html), [транзакционный outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html). Это проверка технических фактов, а не доказательство одинаковой сложности вариантов.

## Дополнительные задания

Семьи `05–12` в каждом грейде и 12 семей недостающих тем подготовлены раньше. Ещё 84 самостоятельных вопроса добавлены по материалам Python, PostgreSQL, HTTP и надёжности сервисов. Их ключи и прямые ссылки на документы сведены в [отдельном списке](13-backend-question-sources.md). Автоматические тесты проверяют коды, структуру вариантов, ключи после перестановки ответов и покрытие навыков. Соответствие сложности грейду они не доказывают.

Для сравнения форматов заданий можно посмотреть открытые [практические упражнения Exercism по Python](https://exercism.org/tracks/python/exercises), [руководство PostgreSQL с запросами](https://www.postgresql.org/docs/16/tutorial.html) и [вопросы по Backend на roadmap.sh](https://roadmap.sh/questions). Вопросы из них в банк дословно не переносились. Публичная подборка сама по себе не подтверждает грейд или качество нашего теста.

## Что проверено и что ещё предстоит

- При необходимости лист со всеми вариантами можно собрать командой `cd backend && uv run python generate_question_review_sheet.py`.
- При первоначальной проверке у части заданий Middle и Senior были слишком очевидные неверные варианты. Их заменили на более правдоподобные технические альтернативы. Действительную сложность обновлённых заданий ещё нужно проверить на ответах людей разных уровней в B-32; наличие правильных ключей этого не подтверждает.
- Для новых вопросов есть источники и структурные проверки, но независимой технической оценки всего банка пока нет. Участникам без опыта Backend не нужно решать вопросы ради формальной отметки.
- Автоматические проверки требуют уникальных кодов, существующих ключей ответов, трёх версий каждого Backend-задания и покрытия всех трёх грейдов. Они не могут доказать правильность технического ответа.
- При открытии первого набора API фиксирует основную и запасную версии всех обязательных заданий. Обновление банка не меняет начатую попытку. После завершения первого набора запасная версия используется для единственной пересдачи всех четырёх навыков; она получает собственный трёхдневный срок. После второй неудачи предлагаем уровень ниже. Для Junior новый цикл можно начать через неделю; при переходе с подтверждённого нижнего грейда на следующий открывается новый цикл повышения.
- Чтобы судить о сложности и порогах грейда, нужны реальные ответы людей разных уровней. Это задача B-32, а не условие готовности подготовленного банка. Без таких данных банк нельзя называть статистически откалиброванным.
- Вопросы Frontend и DevOps сохранены, но в каждой паре сейчас только по одному исходному вопросу. Эти направления не открыты для теста в B-01.
- Backend-набор дополняет вопросы с выбором ответа открытыми заданиями: объяснением решения и кодом; у Middle и Senior есть рабочая ситуация. Для двух Middle-задач с кодом доступен пробный запуск; для остальных задач с кодом изолированный исполнитель пока не подготовлен. Результат всего набора не равен полной оценке квалификации Senior. Качество модельной оценки и сложность заданий нужно проверять на ответах людей (B-32).
- Новая схема присвоения грейда требует итоговых 75% и не менее 50% по каждому обязательному навыку. Правило в `backend/app/core/grade_policy.py` подключено к API набора, но качество порогов на ответах людей пока не проверено.
