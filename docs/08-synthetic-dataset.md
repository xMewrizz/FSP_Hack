# Проверочный набор кандидатов и потребностей

Генератор `ml-service/generate_synthetic.py` создаёт данные для проверки подбора без запуска backend. По умолчанию это 60 вымышленных кандидатов и пять запросов работодателя на сотрудника (в данных они называются «потребностями»). Seed фиксирован: `2026`. Число 60 взято как небольшой рабочий объём: девять комбинаций трёх специализаций и трёх грейдов получают по шесть или семь кандидатов.

Это выбранные нами сценарии для первого прогона, а не требование ТЗ именно к этим пяти вакансиям. Три Backend-запроса покрывают грейды, для которых подготовлены задания; Frontend и DevOps добавлены для проверки профилей других направлений. Все суммы указаны в рублях до вычета налога.

| Запрос | Обязательные навыки | Формат и город | Зарплата |
|---|---|---|---|
| Backend Junior | Python, PostgreSQL | удалённо, Казань | 110–160 тыс. ₽ |
| Backend Middle | FastAPI, PostgreSQL, Redis | гибрид, Москва | 190–270 тыс. ₽ |
| Backend Senior | PostgreSQL, Docker, Kafka | удалённо, Санкт-Петербург | 290–400 тыс. ₽ |
| Frontend Middle | React, TypeScript, CSS | гибрид, Москва | 180–260 тыс. ₽ |
| DevOps Junior | Linux, Docker, CI/CD | удалённо, Новосибирск | 120–180 тыс. ₽ |

Каждый из 60 кандидатов сопоставляется с каждым из пяти запросов: 60 × 5 = 300 сочетаний. Это полный вход для прогона подбора, а не 300 готовых оценок качества. Для первого ручного разбора отдельно отобраны 30 сочетаний — по шесть на запрос: подходящий профиль, профиль с недостающими навыками, другой грейд, другое направление, профиль без ФСП и профиль без описания резюме. Если одна категория уже представлена выбранным кандидатом или нужного профиля нет, скрипт берёт другого, чтобы сохранить шесть разных кандидатов на запрос.

Запуск из корня репозитория:

```bash
python ml-service/generate_synthetic.py
python -m unittest discover -s ml-service/tests -v
```

Файлы в `ml-service/data/synthetic_v1/`:

| Файл | Что внутри |
|---|---|
| `candidates.json` | Профили: специализация, заявленный и подтверждённый грейд, навыки, город, формат, ожидание зарплаты, наличие резюме и достижений ФСП. |
| `needs.json` | Пять потребностей с обязательными навыками, форматом, городом и зарплатой до вычета налога. |
| `all_pairs.jsonl` | Все 300 сочетаний запроса и кандидата для запуска и разбора результатов подбора. Меток релевантности нет. |
| `review_sample.jsonl` | 30 сочетаний для первого ручного разбора с пустыми полями оценок двух участников. |
| `manifest.json` | Seed, размер, покрытие категорий и SHA-256 файлов. |

Все профили, результаты теста и достижения ФСП вымышлены. В наборе нет имён, контактов и реальных ФСП ID. Подтверждённый грейд заполнен только у части Backend-профилей, для которых в B-01 открыт тест; оценка теста у них тоже синтетическая. Эти значения нужны для проверки сортировки, а не для измерения точности самого теста. Профили Frontend и DevOps могут иметь заявленный грейд, но не подтверждённый.

Для каждой потребности в наборе есть хотя бы один кандидат с той же специализацией и грейдом, всеми перечисленными навыками, подходящим форматом, городом и ожиданием зарплаты в пределах предложения. Есть кандидаты без истории ФСП, без подтверждённого грейда и без описания резюме. Это проверка разнообразия данных, а не готовые метки релевантности.

В `review_sample.jsonl` поля `reviewer_1`, `reviewer_2` и `final_label` оставлены пустыми. Два участника команды размечают эти сочетания независимо по правилам из [плана валидации](04-validation-dataset-model.md), затем разбирают расхождения. Метки нельзя вычислять формулой подбора. Исходный файл с пустыми метками оставляем неизменным; заполненные оценки сохраняем отдельно. Для расчёта Precision@3 и nDCG@5 потребуется разметить как минимум кандидатов, которых алгоритм выводит в верхние позиции по каждому запросу, и согласовать способ оценки всей выдачи. Выборка из 30 сочетаний сама по себе не даёт этих метрик.

Набор сейчас существует как файлы. Модели данных уже добавлены; загрузку в БД и сквозную проверку через API ещё нужно провести. Пять потребностей не покрывают все девять категорий; по ним нельзя делать вывод о качестве подбора для каждого направления и грейда.
