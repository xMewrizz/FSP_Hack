# Frontend: стек, решения и UX

Документ описывает действующий frontend, причины выбора технологий и правила развития интерфейса. Сценарии и API приложения описаны в [документации запуска и API](./03-api-and-run.md), дизайн-бриф — в [спецификации UI](./ui-refactor.md).

## Текущий стек

| Технология | Где используется | Почему выбрана |
|---|---|---|
| React 19 | Компоненты экранов, формы и состояние интерактивных сценариев | Команда уже работает с React; интерфейс состоит из повторяемых карточек, форм, профилей, таблиц и диалогов. Компонентная модель позволяет развивать обе роли без отдельного шаблонизатора. |
| TypeScript в strict-режиме | Типы API, моделей формы и состояний | Помогает выявлять несовпадения с FastAPI-контрактами, особенно в статусах, зарплатных типах и результатах тестов, до запуска приложения. |
| Vite 8 | Локальный сервер разработки и production-сборка | Быстрые HMR и сборка; API base URL можно задать через `VITE_API_URL` при сборке. |
| CSS Modules не используются; обычный CSS | `frontend/src/index.css`, тематические классы в JSX | Нынешняя система использует общие CSS-токены, темы и responsive-переопределения. Именованные компонентные классы остаются читаемыми и не требуют второго способа верстать один и тот же экран. |
| Tailwind CSS 4 | Vite-плагин и CSS import уже подключены | Доступен для utility-слоёв при необходимости, но основной интерфейс пока опирается на существующую CSS-систему. Не добавлять Tailwind-классы выборочно в старые компоненты без плана: смешение утилит и ручных overrides усложняет каскад и визуальную проверку. |
| `frontend/src/api.ts` | REST-клиент и авторизация запросов | Один вход для API, токена и человекочитаемых ошибок; `demoApi.ts` обслуживает локальный демо-режим. |
| Inline SVG-компонент и SVG-графики | Иконки и радар навыков | Нет зависимости от крупной библиотеки компонентов/графиков; формы и палитра соответствуют фирменному оформлению. Графики показывают только данные, которые действительно есть у API. |

### Осознанно не добавлены

- Redux/Zustand: общий объём клиентского состояния пока обслуживается локальным React state и browser storage. Добавлять отдельное хранилище следует, если появятся согласованные кросс-экранные операции, сложная кэш-инвалидация или фоновые синхронизации.
- React Router: навигация MVP — переключение экранов кабинета, а не набор адресуемых публичных страниц. Если понадобятся deep links, back/forward по экранам или отдельные страницы SEO, маршрутизатор станет обоснованным.
- UI-kit и модальная библиотека: существующие брендовые компоненты уже заданы CSS и inline SVG. Для доступности диалогов применяется общий `ModalFrame`, а не ещё один параллельный визуальный слой.
- Chart library: для текущей небольшой radar-визуализации SVG-компонента проще, доступнее и легче для bundle. Сложные интерактивные графики сначала требуют отдельного продуктового требования.

## Архитектурные границы

- `App.tsx` содержит авторизацию, переключение роли и основные сценарии MVP. Перед новым независимым крупным разделом переносить связанные типы и UI в feature-модули, не создавать новые несвязанные глобальные состояния.
- `api.ts` отвечает за сеть, заголовок авторизации, ошибки и режим offline demo. UI не должен напрямую формировать URL backend или скрывать сетевую ошибку успешным пустым ответом.
- `demoApi.ts` повторяет только нужные UX-сценарии и явно считается локальным состоянием в памяти страницы; его данные не являются production-проверкой, статистикой или источником оценки качества.
- API-контракт — источник истины для доступа и вычислений. Frontend скрывает недоступные действия ради UX, но backend самостоятельно повторно проверяет роль, участника, статус и владение ресурсом.
- CSS переменные и семантические классы задают тему, цвет, фокус и адаптивность. Фирменные акценты: синий `#402FFF`, красный `#EC1D35`, нейтральный `#EDEDED`; контрастный текст и ошибки не кодируются одним цветом.

## UX-модальных окон и диалогов

Все блокирующие диалоги используют общий `ModalFrame`:

1. Диалог объявляет `role="dialog"`, `aria-modal="true"` и связывается с видимым заголовком через `aria-labelledby`.
2. При открытии фокус переносится внутрь, `Tab` и `Shift+Tab` остаются внутри окна, `Escape` закрывает его, фон страницы не прокручивается.
3. При закрытии восстанавливается фокус на элемент, открывший окно. У окна есть видимая кнопка закрытия с доступным именем.
4. Клик по подложке закрывает только неразрушающий просмотр. Для формы отправки клик по подложке/`Escape` отменяет черновик только если это не приводит к незаметной потере длительного ввода; критичные подтверждения должны явно описывать действие.
5. Высота ограничена viewport, содержимое прокручивается внутри диалога, на мобильном форма занимает почти весь экран и учитывает safe area.
6. Ошибка формы отображается рядом с формой, объявляется assistive technology, поля имеют видимые подписи, состояние отправки блокирует повторный submit.

Модальные сценарии работодателя и кандидата:

- **Профиль кандидата** — просмотр с понятным заголовком, закрытием и возвратом к поиску; контакты остаются скрытыми до принятия приглашения.
- **Сравнение резюме** — одновременно сопоставляются только выбранные кандидаты; на узком экране столбцы складываются в вертикальные карточки, без вынужденной горизонтальной прокрутки всего окна.
- **Приглашение** — зарплатный диапазон и способ расчёта показаны до отправки; состояния отправки/ошибки не маскируются.
- **Чат принятого приглашения** — история, отправка и автоматическое обновление; только участники принятого приглашения могут читать/писать. Вложения не заявлены.
- **Диалоги и наставничество** — переписка находится в отдельном разделе рядом с принятыми приглашениями. Кандидат отдельно включает доступность быть наставником; поиск показывает только подтвердивших более высокий грейд и совпадающих по навыку. Первый запрос ожидает принятия, после этого открывается текстовый чат.
- **Мобильная навигация** — фиксированы только частые разделы и кнопка «Разделы»; все пункты открываются сеткой без горизонтальной ленты и всплывающих описаний поверх контента. Верхняя панель переносит основное действие на отдельную строку, а кнопки остаются в устойчивой сетке.
- **Банк кандидатов** — профиль и сравнение доступны прямо из карточки, а выбранные резюме сравниваются из закреплённой панели. Таблица с действиями за пределом видимой ширины не используется.
- **Тур демо** — диалог-подсказка удерживает клавиатурный фокус, закрывается по `Escape`, имеет явные «Пропустить» и «Далее».
- **Редактирование вакансии** — намеренно остаётся секцией страницы, а не диалогом: форма длинная, пользователь может сопоставлять её с вакансиями и откликами без скрытия контекста.

## Сравнение навыков и доверие к данным

- Балл matching — отдельная оценка подбора, не процент знания навыков.
- Списки «Найдены в профиле» и «Не указаны в профиле» отражают объяснение API, а не доказанное отсутствие навыка или уровень компетенции.
- Не выводить проценты навыковой совместимости, пока не определены единая шкала, веса и backend-контракт с данными на каждый навык.
- Доступность наставника является отдельным добровольным флагом, не зависит от видимости работодателям. Запросы и сообщения наставничества авторизуются backend по участникам и статусу; контакты кандидата в карточке наставника не публикуются.
- Отсутствующее поле показывать как «Нет данных»/«Не передано», а не как нулевой балл или отрицательный сигнал.
- Результат разбора PDF сначала показывается как неподтверждённый предпросмотр. Только после явного переноса пользователь проверяет и редактирует черновик, затем отдельным действием сохраняет профиль.

## Валидация изменений

Минимальная проверка после frontend-изменений:

```powershell
pnpm --dir frontend exec tsc --noEmit
pnpm --dir frontend run build
```

Для изменений REST-сценариев запускать соответствующие backend-тесты через `uv run --project backend pytest ... -q`. Дополнительно вручную проверить desktop и мобильную ширину: нет горизонтального overflow, диалог помещается в viewport, ошибки доступны, Escape/Tab работают, повторная отправка невозможна во время запроса.

Production-поведение нельзя объявлять подтверждённым только потому, что локальный demo API работает: отдельно проверять реальные роли и разрешения на поднятом backend.
