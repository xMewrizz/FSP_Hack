# Архитектура MVP

Здесь описано, как работают части сервиса. В репозитории есть frontend, API, модели данных, миграции и тесты. Все компоненты запускаются через Compose; ML-сервис может обратиться к локальной Ollama или внешнему API для предложения навыков и проверки отдельных открытых ответов. На тестовом сервере используется модель с идентификатором `gpt-5.6-sol` через сторонний OpenAI-совместимый List API. Основной путь приложения работает без модели. Выбор frontend-стека и UX-правила описаны в [документации frontend](./17-frontend-architecture.md).

## Пользовательский путь

```text
Кандидат: email → профиль → опрос → заявленный грейд → тест → категория → приглашение
Работодатель: email → компания → потребность → категории и кандидаты → приглашение → ответ
```

Категория складывается из специализации и подтверждённого грейда. Кандидат без результатов ФСП остаётся доступен для подбора. Историю тестов и изменения грейда следует хранить отдельно от текущей категории.

## Компоненты

| Компонент | Назначение | Состояние |
|---|---|---|
| Frontend | Два кабинета, формы, подборка, приглашения, вакансии, чаты и демо-режим | React + TypeScript + Vite; рабочие формы подключены к API, доступность диалогов и адаптивная сетка проверяются отдельно |
| Backend | Авторизация, профили, тесты, подбор, приглашения, чаты и правила доступа | FastAPI + PostgreSQL; доступ проверяется на API, включая статус принятия приглашения для чата |
| PostgreSQL | Пользователи, профили, задания, попытки, потребности, приглашения | Контейнер запускается и проходит проверку готовности |
| Redis | Кэш подборок и временное состояние попыток при необходимости | Контейнер описан, не используется |
| ML-сервис | Предложение навыков и весов по тексту; отдельная оценка открытого ответа | На тестовом сервере `gpt-5.6-sol` через List API: живыми запросами проверены подсказка навыков и оценка открытого ответа. Результаты прежних проверок Qwen и Gemini приведены в [отчёте B-27](./20-b27-benchmark-validation-report.md) и [проверке тестов](./23-browser-grade-audit.md); к текущей модели они не относятся. Три других маршрута — заглушки |

Frontend обращается к backend. Backend проверяет права доступа и работает с базой. ML-сервис вызывается только для отдельных операций и получает лишь нужные для них данные.

Подбор уже подтверждённых кандидатов работает и при недоступной LLM. Ответ на обязательное развёрнутое задание сохраняется до обращения к модели; если проверка сорвалась, кандидат может повторить её позднее без переписывания ответа. До итоговой оценки грейд не присваивается. Для внешнего API передаются только текст потребности либо вопрос, критерии, эталон и ответ кандидата — в зависимости от вызванного сценария. Настройка провайдера и порядок запуска описаны в [инструкции](./03-api-and-run.md).

## Данные и границы доступа

Основные сущности: пользователь и роль, профиль кандидата, компания, специализация, задание и вариант, попытка теста, подтверждённая категория, потребность работодателя, приглашение и сообщения его принятого диалога, вакансия и отклик, связь с ФСП ID и достижения. На уровне backend кандидат читает только свои приглашения и отклики. Работодатель получает публичную часть профиля; контакты возвращаются только после принятого приглашения от этого работодателя либо отклика кандидата на его вакансию. Фильтр в интерфейсе не заменяет проверку доступа в API.

Согласия на обработку и публикацию профиля хранятся раздельно с датой и версией текста. До публикации профиля в поиске проверяется соответствующее согласие. Пароли хранятся в виде стойких хешей, токены имеют ограниченный срок жизни. Перед сдачей нужны проверка ролевого доступа и сценарии отзыва согласия.

## Связь с ФСП

В демо backend обращается к локальному набору тестовых достижений по введённому ФСП ID. Ответ может быть пустым; это не ошибка и не основание исключать кандидата. В интерфейсе нельзя выдавать тестовые записи за сведения официального реестра.

Будущая интеграция состоит из двух независимых частей: вход или привязка учётной записи через Keycloak/OIDC и получение достижений из реестра ФСП. Наличие OIDC само по себе не даёт данных реестра. После публикации API ФСП понадобится отдельный адаптер данных и проверка происхождения достижений.

## Производительность и сбои

В выдачу работодателя попадают кандидаты с подтверждённой категорией, разрешившие публикацию профиля. Заявленный грейд нужен для выбора теста и не даёт права попасть в подбор или банк работодателя. Внутри подходящей категории кандидатов сортируем по соответствию потребности. Поиск должен открываться постранично и не тормозить при росте базы. Кэш добавим после замеров и будем обновлять при изменении профиля, теста или потребности. Если LLM недоступна, используем готовые задания и обычный расчёт совпадения. Время ответа пока не измеряли.
